# 决策记录: 寄存器分配器重写——把栈搬运从 50.8% 压到极限

Status: draft — 在 `feat/stack-isa-opt` 上按里程碑推进寄存器分配器；每个里程碑独立过全量门禁与 `prof` 实测，未达标即回退该里程碑。

## 问题

动态剖析（`benches/bottleneck.rs`，`prof` 特性）实测：单次调用 664 条指令、3443.8ns、5.19ns/条，构成是

| 类别 | 占比 |
|---|---|
| 栈搬运（PUSH_IMM/PUSH_IMM8/PUSH_REG/POP_REG/DROP/DUP） | **50.8%** |
| 混淆开销（NOP 10.7 + SWAP 5.1 + NOT 5.0） | 20.8% |
| 真实计算（ADD/XOR/AND/SUB/CMP） | 21.5% |
| 控制流（JMP） | 2.7% |

`#[track_caller]` 归因（编译期，独立方法）给出同样的结论：47% 的搬运来自
`compile_expr` 33.7%、`compile_local` 13.3%、`hoist_arg` 7.7%、`compile_assign_op` 4.9%。
两个方法互证，可以确定：**性能瓶颈是「表达式求值一律走栈」这个求值模型**，
不是某几条指令的开销，也不是窥孔能解决的事（窥孔实测只有 0.7% 可删）。

现有的 `compile_expr` 把每个中间值压栈；`compile_expr_to_reg` 只覆盖了极少数形参搬运场景。
运行时已有 `regs: Vec<u64>`（容量 `DEFAULT_REGISTER_CAPACITY`，`src/state.rs:160`），
寄存器是现成的，缺的是**编译期的分配决策**。

## 决策

**1. 走「表达式内线性寄存器分配」，不做全局图着色。** 理由是收益/成本比：
栈搬运的绝对多数来自表达式内部的中间值，而不是跨语句的长生命周期变量。
先把每个表达式的求值从「压栈」改成「分配到虚拟寄存器，用完即释放」，
就能吃掉最大的一块，且改动被限制在 `compile_expr` 及其递归调用内，不触碰调用约定与帧布局。

**2. 分四个里程碑，每个独立验收、独立回退。**

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 | 虚拟寄存器池 + 引用计数释放（只做算术/位运算表达式，不含分支与调用） | 该形态函数的 `prof` 栈搬运占比下降 ≥20 个百分点；863 项测试全绿 |
| M2 | 局部变量常驻寄存器（`compile_local` / 变量读写不再压栈），超出容量溢出到帧槽 | 同上，且 `real_world` ABBA 中位数改善可重复 |
| M3 | 实参搬运与复合赋值走寄存器（`hoist_arg`、`compile_assign_op`） | 同上 |
| M4 | 与混淆层对接：寄存器形态的指令必须接入指令替换，缺口不得扩大 | 缺口测试通过，且 `prof` 中 SWAP/NOT 仍覆盖新指令 |

**3. 硬约束**
- 每个里程碑都要有 `prof` 前后对照（栈搬运占比）与 `real_world` 的 ABBA 中位数（≥3 轮交替）；
- 任一里程碑若拿不到「栈搬运占比下降 ≥20 个百分点」，该里程碑回退，并把原因写进本决议；
- 不改 handler 语义，不新增 opcode（除非某里程碑单独出决议）；
- 混淆强度不得下降：新增的寄存器形态指令必须能被指令替换覆盖，否则视为扩大保护缺口；
- 全量门禁（当前 863 项）每个里程碑必须全绿，重构不得沉默地改变行为。

## 提案

第一轮（M1）的具体形态：

1. 在 `Compiler` 上维护 `vreg_pool: SmallVec<u8>` 与每个虚拟寄存器的 `last_use`；
2. `compile_expr` 求值统一改为「结果写入指定虚拟寄存器」，递归子表达式各自申请、用完归还；
3. 二元运算 `a op b` 编译为：`dst = vreg(); compile_sub(a, dst); tmp = vreg(); compile_sub(b, tmp); emit_binop_reg_reg(dst, tmp); free(tmp)`；
4. 只有池耗尽或跨语句存活时才回落到栈（先保证正确性，再谈减少回落）；
5. 先只覆盖 `BinOp::Add/Sub/Mul/And/Or/Xor/Shl/Shr`，其它形态保持原路径，避免一次改太大。

观测方式：`AEGIS_DUMP` 看发射形态是否真的变成寄存器形态；`prof` 看运行期栈搬运占比；
`cargo bench --bench real_world` + ABBA 看端到端。

## 验收标准

- M1 完成后：同一负载的 `prof` 分布中「栈搬运」类占比从 **50.8% 降到 30% 以下**；
- `real_world` 的 ABBA 中位数（≥3 轮交替取中位数）相对基线有可重复改善，且方向一致；
- 863 项测试全绿，混淆缺口测试不退化；
- 每个里程碑的实测数字与回退记录都写进本决议。

## 风险

- **正确性风险最高**：寄存器分配错了不会崩溃，只会算出错值。`gcd_step` 那次（`POP r; PUSH r` 误判为空转）
  已经证明这类错误只有全量测试能拦住，因此每个里程碑都必须跑全量门禁，不许只跑单元测试。
- **可能拿不到预期收益**：若栈搬运主要来自「变量读写」而非「表达式中间值」，M1 的收益会远低于预期；
  这种情况下应直接把资源投到 M2，而不是在 M1 里继续磨。
- **混淆缺口可能扩大**：寄存器形态指令若不接入指令替换，会成为新的可识别特征。
  M4 之前不得声称「完成」，否则等于用保护强度换性能。
- **分支漂移**：本分支与 `feat/reg-isa-stage1` 的编译器会持续分叉，移植成本随时间上升；
  约定是本分支为栈式 ISA 的主线，寄存器 ISA 分支只作对照。
- **明知放弃**：本轮不做全局图着色、不做跨函数寄存器分配、不做基于活跃区间的栈槽复用。
  它们能再挤出一部分，但成本与风险都比 M1–M4 高一档，留待有实测需求时再议。

## 备选方案

- **只做栈顶缓存（TOS in register）**：改动比完整分配器小，能吃掉相当一部分 `PUSH/POP`，
  但不解决变量读写的搬运；且它改变求值模型，与 M1 有重叠，先做分配器更彻底。
- **降混淆换性能**：`NOP`+`SWAP`+`NOT` 占 20.8%，是最快见效的一刀，但直接降低保护强度；
  本决议不采纳，因为本分支的目标是「同等保护强度下提速」。
- **维持现状收口**：栈式 ISA 在 3443.8ns/次 已可接受于冷路径；若 M1 拿不到栈搬运降到 30% 以下，
  应回到这个选项并把结论写进决议。
