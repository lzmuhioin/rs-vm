# 决策记录: 栈式 ISA 效率优化试验（从 main 分叉，独立于寄存器 ISA）

Status: draft — 在 `feat/stack-isa-opt`（自 `main` `b17c9a9` 分叉）上做栈式 ISA 的效率优化试验，先立测量基线再动手；寄存器 ISA 分支保留为已验证的备选。

## 问题

寄存器式 ISA（`feat/reg-isa-stage1`，25 个提交、124 条 opcode）已验证可行：真实形态函数 Standard ≈470x、Paranoid ≈1260x，三档结果一致，门禁 916 绿。但它有三个问题：

1. **是验证性改造，形态变更大**：新增 28 条融合指令，`BASE_OPCODES` 只能末尾追加，宏与运行时要同步升级，长期维护成本高。
2. **保护特征变了**：寄存器语义的指令流解密后比栈式好读；同时融合指令不接指令替换，形成新的保护缺口（现已用测试盯住，仅占约 14%、单形态 <2.6%）。
3. **收益有上限**：栈搬运仍占 47%，根因是**没有寄存器分配**，属重写级工作，寄存器 ISA 本身吃不到。

而栈式 ISA 技术成熟、改动面小、保护形态未被改变。寄存器 ISA 这一轮积累的**方法论**（而非产物）可以直接搬过来用——这是本试验的主要动机。

## 决策

**1. 试验在独立分支进行，不合并、不回改 `main`。** 分支 `feat/stack-isa-opt` 自 `main` 分叉；寄存器 ISA 分支原样保留，作为已验证的对照与备选。

**2. 先建测量基线，再动手优化。** 现有指令构成数据（9960 条，PUSH_REG 27.4%、POP_REG 19.6%、`POP_REG;PUSH_REG` 相邻对 10.0%）**全部来自寄存器 ISA 的编译器，不能直接套用到栈式 ISA**。开工前必须在本分支重测：
   - 迁移测量工具：`benches/vm_workloads.rs`、`benches/real_world.rs`、`benches/call_overhead.rs`、`scripts/vm-opcode-census.sh`、`AEGIS_DUMP` 钩子、`OP_COUNT` / `FUSED_IMM_EMITTED` 计数器、`#[track_caller]` 搬运归因（分别源自 `feat/reg-isa-stage1` 的 `932d95c`、`d03b32c`、`701bbff`、`341bb85` 及其中的宏内改动）。
   - 在本分支产出：指令构成表、相邻指令对（bigram）表、三个 bench 的基线数字。

**3. 优化按「数据排序 + 风险递增」推进，一轮只做一层**
   - 第一层（窥孔，零语义风险）：删掉 `PUSH;POP` 空转；`POP_REG;PUSH_REG` 在源=目标时删掉、否则改直传；`DROP;DROP` 合成一条。
   - 第二层（超指令）：仅对第一层之后仍居前的相邻对做融合，且必须先确认保护缺口不扩大（缺口由测试盯住）。
   - 第三层（结构性）：栈顶缓存、局部变量直接寻址、循环不变量外提。任一项动工前单独出决议。

**4. 硬约束（与 `AGENTS.md` 一致）**
   - 不改 handler 语义；`DROP` 不动标志位；不许 `#[allow]` 掩盖告警。
   - 每轮改动必须有「指令条数下降」的确定性证据（`OP_COUNT`），性能结论必须 **ABBA 交替 + 中位数**并标「实测/推断」。
   - 不加保护缺口；新增融合指令必须同轮接入 Paranoid 的混淆回退，或明确写进缺口测试。
   - 门禁 `./scripts/check.sh` 每轮全绿；慢于基线的改动删掉并记录。

**5. 验收标准**：在同一台机器上，`real_world` 与 `vm_workloads` 的 ABBA 中位数相对 `main` 基线有可重复的改善，且指令条数同步下降；否则视为无效，回退。

## 提案

第一轮（只做测量，不改编译器）：

1. 把测量工具从 `feat/reg-isa-stage1` 搬到本分支——`benches/vm_workloads.rs`（`932d95c`）、
   `benches/real_world.rs`（`d03b32c`）、`benches/call_overhead.rs`（`701bbff`）、
   `scripts/vm-opcode-census.sh`（`341bb85`），以及宏内的 `AEGIS_DUMP` 钩子、`OP_COUNT` 计数器、
   `#[track_caller]` 搬运归因。搬运后先跑门禁，确认没有把寄存器 ISA 的语义改动带进来。
2. 在 `main` 基线上产出三张表：指令构成（各 opcode 占比）、相邻指令对（bigram）、三个 bench 的
   ABBA 中位数。**这是后续所有优化的对照基准，先落地再谈改代码。**

第二轮（窥孔，按第一轮数据排序）：

1. `PUSH;POP` 空转直接删除；
2. `POP_REG;PUSH_REG`：源=目标则删除，否则直传；
3. `DROP;DROP` 合成一条。
每条都要有「指令条数下降」的计数证据 + ABBA 实测，慢于基线的立即回退。

## 验收标准

- 测量基线（第一轮）落库：三张表 + 三个 bench 的 ABBA 中位数，可在任意机器复现；
- 每项优化：`OP_COUNT` 指令条数确定下降，且 `real_world` / `vm_workloads` 的 ABBA 中位数相对
  `main` 基线有可重复改善；
- 门禁 `./scripts/check.sh` 全绿（当前 `main` 基线 908 项，移植工具后按实际数字）；
- 保护缺口不扩大：新增/改动的指令若绕过指令替换，必须同轮接入 Paranoid 回退或更新缺口测试。

## 风险

- **数据不可移植**：现有指令构成数据来自寄存器 ISA 的编译器。若第一轮测量跳过、直接套用旧数字，
  会重复本次寄存器 ISA 工作中反复出现的方法论错误（三次结论被 ABBA 推翻）。故第一轮只测量、不改代码。
- **窥孔收益可能很小**：栈式 ISA 上 `PUSH;POP` 是否成对出现，取决于编译器是否已消除，未测前不能假定；
  若第一轮数据显示可删部分不足 5%，本试验应直接收口（见备选方案第三条）。
- **超指令会扩大保护缺口**：融合指令不接指令替换是已知缺口，栈式 ISA 上做超指令会复制这个问题，
  因此把它排在第二层、且要求同轮接入回退。
- **明知放弃**：本轮不追寄存器分配器（吃掉 47% 搬运的最终解）与栈顶缓存（改变求值模型），
  它们属重写级，与「快速验证栈式 ISA 是否值得优化」的目标冲突。
- **分支散乱**：同时维护 `feat/reg-isa-stage1`（25 提交）与本分支，工具与决议可能两边漂移；
  约定是以本分支的决议为准，寄存器分支只作对照，不再回改。

## 备选方案

- **直接做栈顶缓存（跳过窥孔）**：收益可能更大，但它改变求值模型（栈顶常驻物理寄存器），实现与调试成本高，且一旦失败会污染整条分支；先做零风险的窥孔能快速验证「测量—改动—复测」闭环是否成立。
- **直接在栈式 ISA 上做寄存器分配器**：这是最终解（可吃掉 47% 搬运 + 11% 复合赋值），但它同时重写表达式求值、变量访问与调用约定，属重写级项目，不宜与「试验可行性」混在一轮。
- **维持现状不优化**：栈式 ISA 已经是 `main` 的稳定实现，474x/1260x 的倍率在冷路径场景可接受。若本试验两轮内拿不到可重复的两位数改善，则应回到这个选项，并把结论写进决议收口。

### 第一轮测量结果（`main` 基线，实测）

工具：`AEGIS_DUMP`（指令构成）+ `AEGIS_STK`（`#[track_caller]` 搬运归因）同时开，解析成指令流后配对。

**指令构成（11280 条）**：PUSH_REG 24.3%、POP_REG 15.2%、DROP 12.6%、JMP 5.7%、DUP 5.2%、
HEAP_LOAD64 5.2%、HALT 4.3%、HEAP_STORE64 3.8%、XOR 3.4%、NATIVE_READ 3.1%。

**搬运归因（4465 次）**：`expr.rs:47`（compile_expr）33.7%、`stmt.rs:33`（compile_local）13.3%、
`mod.rs:315`（hoist_arg）7.7%、`stmt.rs:294+315`（compile_assign_op）4.9%、`mod.rs:335` 4.5%、
`expr.rs:1029` 4.1%、`control.rs:864+865` 2.8%。与寄存器 ISA 分支同法归因高度一致
（compile_expr 33.7% vs 30.6%），说明搬运根因是**求值模型**，与 ISA 形态无关。

**相邻对配对（11346 条指令流）**：

| 相邻对 | 总次数 | 同寄存器（纯空转，可删） | 异寄存器 |
|---|---|---|---|
| `PUSH;POP` | 338 | **76** | 262 |
| `POP;PUSH` | 990 | **630** | 360 |

**结论：同寄存器合计 706 条，占 11346 的 6.2%，超过决议定的 5% 止损线，值得做。**

`POP r; PUSH r` 是彻底的死代码：栈深不变、栈顶不变、r 的值最终也不被这一对改变；
`PUSH r; POP r` 同理。两者都可在发射阶段直接抹掉，不需要新 opcode、不改 handler 语义。

**风险与验证方式**：删掉后 r 不再被写入。若上层寄存器分配器依赖「POP 会写 r」，
行为会变——因此以全量 863 项测试等价性为准，并单独确认 `compile_expr`/`compile_local`
两条主路径的产物在删掉空转后仍能跑通全部既有测试。

### 否决：抹掉同寄存器空转 `POP r; PUSH r` / `PUSH r; POP r`（实测失败）

按上一节的数据（706 条同寄存器，6.2%）在发射阶段加了拦截：记录上一条栈搬运
（PUSH/POP、寄存器号、发射前字节位置），若下一条是同寄存器且反向，就把两条一起
`truncate` 掉；其它任何指令都把记录清空。宏单测 63 项全绿，但**全量门禁挂了一项**：

```
tests/division.rs:91  test_gcd_step
  assert_eq!(gcd_step(48, 18), 12)  →  实得 0
```

**为什么推理错了**：我按「栈深不变、栈顶不变、寄存器 r 最终值不变」判定整对可删，
但这是**只看了这三样状态**得出的。实测说明寄存器分配器依赖了被删指令的**其它副作用**
（或发射期状态，例如指令编码/死代码插入依赖当时的位置与长度，截断后后续编码偏移），
这一层没有在「栈 + 寄存器值」的语义模型里体现出来。

**决定：否决这条改动，回到 `main` 基线。** 若要重试，必须先做两件事：
1. 用 `AEGIS_DUMP` 把失败用例（`gcd_step(48, 18)`）的实际发射序列打出来，看清那一对
   同寄存器搬运前后到底有哪些指令，确认「同寄存器」是否真如数据所示成对相邻；
2. 查清 `emit_op` 里死代码插入与编码是否依赖字节位置（若依赖，`truncate` 回滚字节
   会改变后续所有指令的编码，不能用「截断」实现删除，只能改成「不发射」）。

**教训**：静态相邻对统计只能说明「有机会」，不能说明「删了就等价」。
等价性必须以全量测试为准——这次正是靠 863 项里那 1 项拦下来的。

### 根因查清：`POP r; PUSH r` 不是空转，是「把栈顶读进寄存器」

把 `gcd_step(a, b)` 单独拿出来打发射序列（`AEGIS_DUMP=1 AEGIS_STK=1`），开头就是：

```
OP F1 (NATIVE_READ)        ← 取实参 a
OP 04 (POP_REG)   ← mod.rs:315 (hoist_arg)
OP F1 (NATIVE_READ)        ← 取实参 b
OP 04 (POP_REG)   ← mod.rs:315 (hoist_arg)
OP 03 (PUSH_REG)  ← expr.rs:47
OP 23 (XOR)
...
```

**我此前判定「整对空转」是错的。** 逐状态推一遍：

| | 执行前 | `POP r` 后 | `PUSH r` 后 |
|---|---|---|---|
| 栈 | `[..., X]` | `[...]` | `[..., X]` |
| 寄存器 r | 旧值 | **X** | **X** |

栈确实恢复原样，但**寄存器 r 的最终值是 X，不是它原来的值**。我上面写「寄存器 r 最终值不变」，
是把「不变」的对象搞错了——不变的是**栈**，不是**寄存器**。

所以 `POP r; PUSH r` 的真实语义是「**把栈顶读进 r，同时保持栈**」，也就是一条
`PEEK_REG r`。`hoist_arg`（`mod.rs:315`）正是用它把实参搬进寄存器——删掉它，实参就丢了，
`gcd_step(48,18)` 自然算出 0。

**两个方向的结论必须分开**：

| 相邻对 | 同寄存器时是否空转 | 依据 |
|---|---|---|
| `PUSH r; POP r` | **是**（r 读回同一个 r，栈复原） | 真·死代码，可删 |
| `POP r; PUSH r` | **否**（r 被赋成栈顶值，栈复原） | 是「读栈顶进寄存器」的惯用写法 |

上一节把两者合并成「706 条死代码」是我统计口径的错误：只按寄存器号相同就归为一类，
没有区分方向。实际可无条件删除的是 `PUSH r; POP r` 那 **76 条（0.7%）**，收益微不足道。

**真正有价值的优化方向因此变成**：为 `POP r; PUSH r`（630 条，5.6%）提供一条
单指令形态 `PEEK_REG r`（2 字节 vs 4 字节，省一次派发）。这**需要新增 opcode**，
属第二层（超指令）范畴，按决议须同轮评估保护缺口。是否值得做，交给下一轮决议。
